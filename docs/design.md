# Устройство ingest

Решение от 2026-11-05 по `ING-1`.

## Путь запроса

1. `X-Ingest-Key` передаётся `DragonflyApiTokenReader` из `aiip-kit`.
   Он читает digest в Dragonfly и при промахе вызывает служебный API
   `projects`. Недействительный ключ отклоняется до чтения тела.
2. Проверяется scope, затем атомарный token bucket в Dragonfly: 5
   запросов в секунду и всплеск до 20 на проект. Недоступный Dragonfly
   означает отказ, а не обход лимита.
3. Тело читается потоково до 256 КиБ, проверяется схема. Alertmanager
   принимает не более 50 алертов. `project_id` и `environment_id`
   сверяются с привязкой токена; ключ без окружения отклоняется.
4. Для каждого факта создаётся `receipt_id` и `MessageV1` с `token_id`,
   проектом, окружением и `lifecycle_version`. `AmqpPublisher` ждёт
   publisher confirm и mandatory routing. Только после этого клиент
   получает `202`.

`alert.received` идёт в `incidents.commands`, `deployment.received` — в
`projects.commands`. Сервис не ведёт дедупликацию и не открывает БД.
Для Alertmanager `receipt_id` детерминирован по `token_id`, receiver,
fingerprint, startsAt и status. При частичной публикации пачки и повторе
все подтверждённые ранее алерты сохраняют ID квитанций; получатель
дедуплицирует факт. Неиспользуемые поля нативного webhook отбрасываются
перед публикацией.
Список `service_ids` во входном alert не является доказательством
принадлежности сервиса проекту: `incidents` обязан сверить его с каталогом
перед созданием инцидента. Повтор после неопределённого исхода публикации
может прийти с новым `receipt_id`; дедупликация факта — обязанность
получателя по `(project_id, token_id, source, source_event_id)`.

## Размещение и наблюдаемость

Две реплики за Traefik, без локального состояния. `/ready` проверяет
Dragonfly. RabbitMQ подтверждает каждую публикацию; ошибка становится
`503`. JSON-логи, OpenTelemetry для FastAPI, Redis и httpx, метрики
Prometheus на `/metrics`.

## Ограничения текущего этапа

RabbitMQ `basic.nack` для `alert.received` переводится в `429` с
`Retry-After`; отказ соединения, timeout и unroutable остаются `503`.
AMQP 0.9.1 не передаёт причину `nack`, поэтому при редкой внутренней
ошибке очереди ответ также будет `429`. Предел числа, байтов и возраста
объявляется в очереди потребителя `incidents` и требует живой проверки.
Служебный токен для вызова `projects` зависит от
`AUTH-4`, чтение API-токена — от `PRJ-6`; unit-тесты используют fake из
`aiip-kit`.
